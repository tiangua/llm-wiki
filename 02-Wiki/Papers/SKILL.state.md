# SKILL.state: 用显式执行状态取代对话历史

**arXiv**: [2608.26263](https://arxiv.org/abs/2608.26263)（v1 2026-08-26，v2 2026-08-28）  
**领域**: Artificial Intelligence, Multiagent Systems (cs.AI, cs.MA)  
**状态**: **已被 EMNLP 接收**

---

## 📋 一句话

长程 Agent 不需要不断增长的对话历史。用一份**小而结构化的执行状态**代替它，prompt 大小恒定，累积 token 从 O(T²) 降到 O(T)，而且准确率通常还更高。

---

## 🎯 它要解决的病

现有 Agent 运行时靠「不断往对话历史里追加观察、动作、中间推理」来维持执行。后果：

- **延迟退化**：prompt 越长，每步越慢
- **上下文污染**（context poisoning）：几十步之后，过期观察、陈旧状态、失效的工具输出、历史推理全堆在一起，模型每一步都得重新判断「哪些信息现在还算数」
- **复杂度**：对话式运行时提示长度 |C_t| = O(t)，累积 token = **O(T²)**

---

## 🏗️ 架构：每步只看三样东西

执行步骤 t，模型收到的输入**严格**是三元组：

```
A_t = (P, Σ_t, O_t)
```

| 符号 | 含义 |
|------|------|
| **P** | 不可变的程序化技能规范（persona、动作空间、环境规则） |
| **Σ_t** | 当前结构化执行状态 |
| **O_t** | 来自环境的最新观察 |

模型**收不到**此前的观察、此前的动作、此前的推理轨迹。

模型生成三样东西：

```
(R_t, ΔΣ_t, a_t)
```

- **R_t** — 多步 CoT 推理（生成时完整保留，用于支撑复杂演绎）
- **ΔΣ_t** — 结构化状态补丁，JSON 字典，支持 key 的 mutation 与 deletion
- **a_t** — 要执行的动作

然后：

```
Σ_{t+1} = Σ_t ⊕ ΔΣ_t
```

`⊕` 是运行时的字典合并操作，带 **null 删除语义**（把 key 设为 null 即删除）。

**执行循环**：

1. 接收最新观察 O_t
2. 用 (P, Σ_t, O_t) 构造 prompt
3. LLM 生成 (R_t, ΔΣ_t, a_t)
4. **确定性校验**状态迁移 ΔΣ_t（无效 patch 触发 rollback-retry）
5. Σ_{t+1} ← Σ_t ⊕ ΔΣ_t
6. 执行动作 a_t
7. **永久丢弃推理轨迹 R_t** —— 它永不出现在后续任何 prompt 中

### 复杂度对比

| 运行时 | 提示大小 | 累积 token |
|---|---|---|
| 对话式（ReAct） | O(t) | **O(T²)** |
| **SKILL.state** | **O(\|P\| + \|Σ\| + \|O\|) = O(1)** | **O(T)** |

### 状态 schema 设计

- 状态是**一等运行时抽象**，只保留未来执行必需的信息
- schema **按领域只编写一次**，不是每个任务一次
  - 例：InterCode CTF 全部 100 个不同挑战，复用同一个 5 字段 schema：`discovered_flags`、`tested_hypotheses`、`active_files`、`working_dir`、`cmd_summary`
- **schema 所有权与校验在确定性运行时，不在模型里** → 畸形输出无法破坏持久状态

## ⚠️ 局限

### 1. Sufficient Statistic 假设及其三种失效

核心假设：**执行状态可以被构造成未来执行的充分统计量**——所有与未来动作相关的过去信息，一经发现就能投影进结构化状态。假设成立时，丢弃历史是**无损的**。它在以下三种情形失效：

1. **没有预先已知的固定 schema**，相关状态结构必须在执行中动态发现
2. **早期观察的相关性当时未被识别**，因而从未被提交进状态
3. **任务目标定义在历史轨迹本身之上**（审计、调试溯源、解释过去行为）——此时历史是目标输出，而非可丢弃的开销

### 2. 开放权重模型上收益大幅缩水

Gemma-4-31B 在 T=100 时 SKILL.state 0.42，与 Stateful 的 0.42 **打平**。错误分类显示失败不来自推理能力，而来自**结构化输出遵循能力**：

| 错误类型 | 占比 |
|---|---|
| 状态被整体覆盖/删除（而非增量合并） | **68%** |
| Schema 理解 / 类型强制错误 | 20% |
| JSON 语法/格式疏漏 | 12% |

→ 小模型需配 **grammar-constrained decoding** 才用得起来。

### 3. 其他

- 当前只验证**单智能体**程序化执行。多智能体会引入并发写，要求 `⊕` 具备确定性冲突解决语义，本文未检验
- 跨模型实验仅覆盖 3 个模型，样本偏薄

## 💡 关键判断

**与 [[WikiSkill]] 是互补的，不该放一起比。** WikiSkill 管技能的**离线生命周期**（跨任务、跨迭代沉淀可复用资产），SKILL.state 管技能的**在线执行**（单任务内怎么让上下文不失控）。一个产出技能，一个跑技能，可以直接串起来用。

**自建批评：token 数漂亮，但没报真实推理成本。** SKILL.state 每步都要重算状态，会削弱 KV cache 复用；而传统长 prompt 恰恰能靠前缀缓存摊薄成本。论文只报累计 token，未报耗时/费用。落地前必须按实际缓存策略重估——在强前缀缓存的服务上，16× 的 token 优势有可能被显著吃掉。
